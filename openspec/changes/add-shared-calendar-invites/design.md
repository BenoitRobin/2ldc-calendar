## Context

No source tree exists yet — only `PRD.md` (methodology) and `ARCHITECTURE.md`
(binding stack decisions: SvelteKit/TypeScript, Drizzle ORM over Turso/libSQL,
better-auth, Tailwind CSS + shadcn-svelte, pnpm, Vercel, Playwright). This design
follows those decisions as given rather than re-evaluating them, and covers project
scaffolding plus the data model and route structure needed for the three capabilities
in `specs/`: `user-auth`, `event-calendar`, `event-attendance`. See `proposal.md` for
motivation and `ARCHITECTURE.md` for the stack rationale.

## Goals / Non-Goals

**Goals:**
- Stand up the SvelteKit project skeleton and dev-local database so every later
  change builds on a working repo instead of starting from zero.
- Define the Drizzle schema for accounts, sessions, events, and presence responses
  in one place, shared between better-auth's adapter and application code.
- Define the route/hook structure that enforces role checks server-side per
  `user-auth`.

**Non-Goals:**
- No OAuth/2FA (per `ARCHITECTURE.md`, deferred until asked for).
- No production account provisioning (Turso, Resend, Vercel) — env vars stay blank
  in `.env.example` per PRD phase 10.
- No full admin account-management UI (list/edit/deactivate); this change adds only
  the minimal "create a team member" action `user-auth` requires. Broader account
  management is a candidate for a later change.
- No email notifications on new events or invites in this change — Resend is wired
  as a no-op console-log fallback (per `ARCHITECTURE.md`) but nothing triggers a send
  yet.
- No CI pipeline for Playwright (PRD/ARCHITECTURE both defer this).

## Decisions

### Project scaffolding order
Scaffold in the order PRD phase 3-4 prescribes: SvelteKit skeleton → Tailwind +
shadcn-svelte → Drizzle schema against a local SQLite file → better-auth wired to
that schema. Doing auth before any UI screens means the route-protection hook exists
before there is anything worth protecting.

### Single shared calendar, no invitee table
Because the chosen invite model is "open to all members" (confirmed with the user
during proposal), events need no invitee join table. Every event row is visible to
every authenticated account; the only per-user state is the presence response.
Alternative considered: a `event_invitees` table scoping visibility — rejected as
unnecessary complexity for a team of a few dozen people who all see the same
calendar, and it can be introduced later as a separate change without reshaping the
event or response tables.

### Data model (Drizzle schema, `src/lib/server/db/schema.ts`)
- `user` / `session` / `account` / `verification` tables: generated by better-auth's
  Drizzle adapter via its official `admin` plugin (`defaultRole: 'standard',
  adminRoles: ['admin']`), rather than a hand-rolled `additionalFields.role` column.
  The plugin adds the `role` column plus `auth.api.createUser` (create an account
  without going through public signup) and `auth.api.setRole` — reusing
  better-auth's own primitives for exactly the "admin creates/roles accounts"
  behavior `user-auth` needs, instead of custom code for the same thing. Public
  self-signup is turned off (`emailAndPassword.disableSignUp: true`); every account
  is created through `createUser`, and the target user sets their own password
  through better-auth's password-reset flow (see the bootstrap/team-member risk
  note below), never a password chosen by the admin or the assistant.
- `event`: `id`, `name`, `date`, `startTime`, `endTime` (nullable — an event may be
  all-day or open-ended), `location` (nullable), `description` (nullable),
  `createdBy` (FK to `user`), timestamps.
- `attendance_response`: `id`, `eventId` (FK to `event`, cascade delete — matches the
  `event-calendar` requirement that deleting an event removes its responses),
  `userId` (FK to `user`), `status` (`'oui' | 'non' | 'indecis'`), unique constraint
  on `(eventId, userId)`, timestamps. No response row means "no response yet" — the
  four-state model in `event-attendance` is represented as three enum values plus
  row absence, not a fourth enum value, so "hasn't answered" can never be written
  over accidentally.

### Route structure and role enforcement
- `src/hooks.server.ts`: resolves the session on every request, attaches
  `locals.user`, and rejects (redirect to `/login`, or 403 for direct
  non-navigational requests) any `/admin/**` request whose `locals.user.role !==
  'admin'` — before the route's own `load`/`actions` run, per `user-auth`'s
  server-side routing requirement.
- `/` (or `/calendar`): shared calendar, standard-nav shell, available to any
  authenticated role.
- `/calendar/[eventId]`: event detail + the current user's own presence response
  control.
- `/overview`: attendance overview (read-only rendering for standard users, editable
  cells for admins — same component, an `editable` prop gates the write actions, per
  PRD phase 9's reuse guidance).
- `/admin/events`, `/admin/events/new`, `/admin/events/[eventId]/edit`: event CRUD,
  admin-nav shell.
- `/admin/team`: the minimal "add a team member by email" action from `user-auth`.
- `/login`: public.

### Presence response writes go through form actions, UI updates optimistically
A SvelteKit form action per status change (not a generic PATCH endpoint), so the
server action re-validates the requester matches the response's `userId` (or is an
admin editing another user's cell) on every write — satisfying the
`event-attendance` requirement that admins alone can correct someone else's
response. The client applies the new status to local state immediately on submit and
rolls back only if the action returns a failure, per the optimistic-update
requirement.

### Status color tokens
Four CSS custom properties (`--status-oui`, `--status-non`, `--status-indecis`,
`--status-none`) defined once in the Tailwind config/theme layer and consumed by a
single `StatusBadge` component — never a hard-coded color in a page or component, per
`ARCHITECTURE.md`'s phase 6 guidance. Contrast is checked against these tokens once,
not per usage site.

## Risks / Trade-offs

- **No invitee list means no way to scope an event to a subset of the team.** →
  Accepted trade-off per the confirmed "open to all" model; introducing per-event
  invitees later only adds a join table and a visibility filter, it does not require
  reshaping `event` or `attendance_response`.
- **Deleting an event silently discards every recorded response (cascade delete).**
  → Matches the explicit confirmation requirement in `event-calendar`; the
  confirmation dialog states that responses will be lost, so the loss is a known
  consequence of a confirmed action, not a surprise.
- **Admin bootstrap and "add a team member" both hand password-setting to the new
  user rather than emailing a real link (Resend isn't provisioned yet).** →
  Fallback is the PRD-mandated console-log stub for `RESEND_API_KEY`-less
  environments; the flow must still work by having the admin relay the
  console-logged link manually until Resend is configured. This is a
  development-time limitation, not a design gap — the same code path sends a real
  email once Resend credentials are added.

## Migration Plan

Greenfield — no existing data or deployed version to migrate from. First deploy
follows PRD phase 12: push skeleton, connect Vercel, apply the Drizzle schema to a
fresh Turso database, run the admin bootstrap script once against production, verify
login end-to-end, then delete the throwaway verification account.
